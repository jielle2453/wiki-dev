## 目的

卡多了以後，她在 Obsidian 搜尋框打字、或問 AI「上次那份報價說交期多久」，要等很久。壓力測試（2026-11-09）3 萬張卡時 `kb find` 47～122 s、`kb lookup` 84～111 s。慢在每查一次，都把每張卡打開解析檔頭，再讀內文。

客戶的時刻：她打兩個字（「交期」），幾秒內看到有這兩個字的卡；剛在 Obsidian 改了一張卡、剛退回一句話、同事剛同步進來的卡，下一次查就是新的。

## 決策

D-345（jie 2026-11-11；jacky 2026-11-09 在 #57 定的「SQLite、每台自己建、不推進 git、壞了退回逐卡掃、只存卡上有的」照舊）：

1. 索引是快取：每張檔案卡一列，放在知識庫外的 `%LOCALAPPDATA%\wiki-with-willy\index\`。沒有、壞了、鎖住、讀不了就照舊直接讀卡，不報錯。
2. 每次要讀全部的檔案卡時，先走一遍 `檔案索引/` 比每張的修改時間與大小，只重讀有變的、拿掉不見的。剛改不到 2 秒的，下次一定重讀。
3. 只改 `cards._scan_groups` 一處。只讀的指令一次指令只走一遍目錄。
4. 找字用 SQLite `instr` 比正規化後的標題與內文，不用 FTS5。
5. 背景比對的排程順便更新索引。另給 `kb index rebuild`。

### 實測（2026-11-11，jie 這台，3 萬張假卡放在 5.3 萬個夾、熱快取，各 3 次取中位數）

| | 3 萬張 |
|---|---|
| 現在的 `_scan_groups`（讀每張卡、解析檔頭） | 6.5 s |
| 走目錄、拿每張卡的修改時間與大小（`os.scandir` 遞迴，不開檔） | 2.0 s |
| 現在的 `_walk_cards`（`os.walk`，只拿路徑、排序） | 3.6 s |
| SQLite 讀出全部檔頭（JSON） | 0.13 s |
| SQLite 讀出全部路徑、修改時間、大小 | 0.05 s |
| `instr` 找一個字（「交期」「宏鑫精密」「gs-1v-ue」「不存在的字」） | 0.04～0.07 s |
| 全新建一次 | 7.8 s，65 MB |

量測程式在 scratchpad，沒進 repo；實作照「驗收準則」重量。

## 要做的事

1. **新檔 `scripts/kb/_lib/card_index.py`**（只用標準函式庫的 `sqlite3`）：
   - `db_path(vault)`：環境變數 `WIKI_WITH_WILLY_INDEX_DIR` 有值就用它；沒有用 `%LOCALAPPDATA%\wiki-with-willy\index`（沒有 LOCALAPPDATA 用 `~/.local/share/wiki-with-willy/index`，同 `office.tools_dir` 的算法）。檔名 `<vault.vault_id>-<知識庫絕對路徑（realpath，Windows 再 casefold）sha1 前 8 碼>.sqlite`。沒有 vault id 回 None（不建索引、照舊讀卡）。路徑每次算，不寫進任何狀態檔（D-019 同理）。
   - `changed(vault, rows, deadline)`：「哪幾張變了」只在這個函式。走 `檔案索引/`（`os.scandir` 遞迴；跳過 `.` 開頭的夾與檔、只收 `.md`（不分大小寫），同 `_walk_cards` 的篩法），拿每張的 `st_mtime_ns`、`st_size`，跟 `rows` 比，回 (新增或變了的路徑, 不見的路徑, 這次看到的全部 {路徑: (mtime_ns, size)})。以下也算變了：索引那列的 `mtime_ns` ≥ 那列的 `seen_ns` − 2 秒（剛改不到 2 秒就被記進索引的，下次一定重讀；補 NTFS 計時器粒度與 FAT/exFAT 2 秒精度）。每走一個夾看一次 deadline，過了丟 `TimeoutError`。以後要改問 git 只換這個函式。
   - `groups(vault, deadline=None)`：回 `(groups, broken)`，**格式、排序、broken 的理由句跟現在的 `cards._scan_groups` 一模一樣**。做法：開索引 → `changed` → 變了的逐張讀檔、`parse_front`、算正規化標題與內文 → 這些列與不見的列在**一個交易**裡寫回 → 照路徑排、組出 groups 與 broken。重讀前也看 deadline；過了先把已重讀的那些寫回（下次少讀一些），再丟 `TimeoutError`。
   - `body_hits(vault, keys)`：回 `{key: set(路徑)}`，每個 key 用 `SELECT path FROM cards WHERE instr(body, ?) > 0`（key 已經是 `entities.key` 過的）。索引不能用時回 None。只在同一個指令剛跑過 `groups` 之後用（索引是新的）。
   - `rebuild(vault)`：刪掉索引檔（含 `-wal`、`-shm`）再 `groups(vault)`，回 (卡數, 秒數)。
   - `once(vault)`（context manager）：在裡面，`cards._scan_groups(vault)`（不帶 deadline）第一次照常算、之後回同一份結果，不再走目錄。只給只讀的指令用（見第 4 點）。
   - 錯誤：開不了、讀寫失敗（`sqlite3.Error`、`OSError`）→ 記一行 `.system/hook-errors.log`（source `index`，同一個指令只記一次），這次改走舊的逐卡讀法。`schema_version` 不對、檔壞了（`sqlite3.DatabaseError`）→ 刪掉索引檔，這次逐卡讀，下次重建。鎖住（另一個程式在寫）→ `timeout` 3 秒，等不到就這次逐卡讀、不寫索引。
2. **`scripts/kb/_lib/cards.py`**：
   - `_scan_groups(vault, deadline=None)`：改成呼叫 `card_index.groups`；索引不能用時呼叫原本的逐卡讀法（原本的內容搬成 `_scan_groups_files`，一字不改）。約 45 處呼叫的地方都不改。
   - `_render_index`：不再自己 `_walk_cards` 加 `parse_front`，改用 `_scan_groups` 的結果拿 `標題`、`原檔[0]`。broken 的卡照現在的樣子（`title` 是 None、預設圖示）。產出的 `總目錄.md` 跟現在逐字一樣。
   - 其他函式不動。

## 資料與介面格式

索引檔 `<LOCALAPPDATA>\wiki-with-willy\index\<vault id>-<路徑 sha1 前 8 碼>.sqlite`，WAL：

```sql
CREATE TABLE meta (k TEXT PRIMARY KEY, v TEXT);
-- ('schema_version', '1')
CREATE TABLE cards (
  path     TEXT PRIMARY KEY,   -- 相對總資料夾，正斜線（同 _walk_cards）
  mtime_ns INTEGER NOT NULL,
  size     INTEGER NOT NULL,
  seen_ns  INTEGER NOT NULL,   -- 這列寫進索引的時間（time.time_ns），判斷「剛改不到 2 秒」
  front    TEXT,               -- parse_front 的結果，json.dumps(ensure_ascii=False)；解析不了是 NULL
  error    TEXT,               -- 解析不了的原因，就是現在 broken 的那句（「檔頭解析不了：…」）；解析得了是 NULL
  title    TEXT NOT NULL,      -- entities.key(檔頭「標題」，不是字串就空字串)
  body     TEXT NOT NULL       -- entities.key(檔頭之後的全文)，見要做的事第 3 點
);
```

- 只存卡上有的東西，刪掉索引什麼都不會少。
- 「沒有編號」「編號格式不對」「同編號多張」不存成 error：照現在的規則在組 groups、broken 時判斷，理由句不變。
- `front` 存回來要跟 `parse_front` 的結果相等（字串、清單、數字、布林；實作確認 `_scalar`、`_value` 會產出哪些型別，JSON 存得下）。
- `schema_version` 不是 `'1'` → 當壞掉處理（刪檔重建）。以後改正規化或欄位就加號。

`kb index rebuild [--json]`：見要做的事第 6 點。`kb find --json`、`kb lookup --json`、`kb cards list --json` 的輸出**一個欄位都不變**。

## 驗收準則

假資料：實作寫一支產生程式放 `willy-測試\開發\#57-卡片索引\程式\`（不進 repo）：`kb init` 一個測試庫、`kb folders add` 一個來源夾，照 `cards.header_for` 的檔頭格式替每份檔合成一張卡（不叫模型），內文中英混雜、含兩個字的中文詞；1 萬張、3 萬張各一份。量之前 pyc 先編好（跑一次 `kb --help`），每項 3 次取中位數，跟這台忙不忙（量之前 1 秒的整機 CPU%）一起記。

1. **結果不變**：`card_index.groups` 與 `_scan_groups_files` 對同一個庫回的 groups、broken 完全相等。測試庫涵蓋：一般卡、檔頭解析不了、沒有編號、編號格式不對、同編號兩張、BOM、`.` 開頭的夾與檔、大寫 `.MD`、中文路徑。
2. **任何人改的都跟得上**：每一種改法之後，下一次 `kb find` 的結果與 `_scan_groups_files` 一致：(a) 直接寫檔改一張卡的內文（模擬 Obsidian 手改）；(b) 新增、刪除、改名一張；(c) `kb entity rename`（改很多張的 `實體`）；(d) `kb versions revert` 退回一句做卡的話；(e) 用 `os.utime` 把改過的卡的修改時間設回原值、大小相同（只靠「剛改不到 2 秒」那條抓到）；(f) 2 秒之後再改一次大小相同的內容。
3. **兩個字的詞**：只在某張卡內文出現的「交期」，`kb find 交期 --json` 找得到那張，`hit` 是 `body`。
4. **索引不能用時照舊**：(a) 索引檔不在；(b) 寫成亂碼；(c) `schema_version` 改成 2；(d) 另一個連線鎖住寫入；(e) 索引夾唯讀。各跑 `kb find`、`kb lookup`：結果跟有索引時一樣、exit 0；(b)(c) 之後索引檔被換成新的；`hook-errors.log` 一個指令最多一行 source `index`。
5. **不在知識庫裡**：跑過 `kb find`、`kb changes --background`、`kb index rebuild` 之後，知識庫裡沒有多出任何檔（前後列檔比對）；索引檔在 `WIKI_WITH_WILLY_INDEX_DIR`（測試）或 LOCALAPPDATA（真機）。
6. **只讀的指令只走一遍**：測試把 `card_index.changed` 換成會計數的替身，`kb lookup <有卡的實體>` 一次只呼叫 1 次；`kb find`、`kb cards list` 也是 1 次。
7. **背景更新**：新增一張卡後跑 `kb changes --background`，索引裡有那張（直接查 SQLite）。
8. **`kb index rebuild`**：人讀與 `--json` 的張數等於 `_scan_groups_files` 的卡數；沒有 vault id 時 exit 1、印原因。
9. **總目錄不變**：同一個測試庫，改之前與改之後 `kb cards index` 產的 `總目錄.md` 逐字相同（含 broken 的卡、圖示開與關）。
10. **速度**（索引已建好、熱的）：
    - `kb find`，三種查法（只在內文的兩字詞、實體名、不存在的字）：1 萬張每種 ≤ 3 s；3 萬張每種 ≤ 8 s。
    - 另外記、不設門檻：沒有索引時的第一次 `kb find`；`kb lookup`（實體、型號、不存在的字）；`kb cards list`；一張卡寫完後 `hooks/output_log.py` 的秒數（改之前、改之後各量）；`kb changes --background`（改之前、改之後）；1 千張的 `kb find`。
    - `kb find` 不存在的字會走「還沒整理的檔」（`lookup.wip_hint` → `cards.wip`），那段有一部分不是讀卡。3 萬張超過 8 s 時，用 cProfile 拆時間寫進回報、停下來，不自己改 `wip`。
11. `grep -n "sqlite3" scripts hooks` 只出現在 `card_index.py`。
12. 相關測試全綠（逐檔跑，記 exit code）；`test_repo_hygiene` 綠。

## 確認情境

在測試 vault（`<測試環境>\總資料夾`），plugin 用 worktree 的快照市集裝在知識庫（local），權限模式預設。

1. **自動**：問「哪份檔有提到交期」（「交期」只在一張卡的內文）→ AI 跑 `kb find` 或 `kb lookup`、回答那份檔。
2. **自動**：直接改一張卡的內文加一個新詞（模擬 Obsidian 手改，不經 AI）→ 馬上開新對話問那個詞 → 找得到那張。
3. **自動**：請 AI 整理一份新檔成卡 → 同一個對話接著問那份檔裡的一個詞 → 找得到；再說「退回上一句」→ 再問同一個詞 → 找不到那張新卡。
4. **自動**：刪掉 LOCALAPPDATA 底下這個庫的索引檔 → 問同一個問題 → 照樣答得出來；索引檔又出現。
5. **人眼**：在 Obsidian 的搜尋框（外掛的 `kb find`）打兩個字的詞 → 結果跟改之前一樣、等待時間記下。
