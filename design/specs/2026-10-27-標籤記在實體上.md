# 標籤記在實體上
日期：2026-10-27
狀態：開發中
版本：發行時填
來自：issue #13；併入 無
區域：設定與知識、狀態檔格式、整理成卡、回答、skill 文字

## 目的

標籤（0.23.0，D-231～D-239）只寫在綜合卡檔頭，綜合卡要掛 `synthesis_min_cards`（2）張檔案卡才建（D-114），所以只有一份資料的實體標不上。保單、合約這類「一件一份」的型別幾乎整個型別都是這樣。2026-10-27 API 標籤品質測試（演練資料 8 客戶、8 保單）：第一輪整理完 8 張保單全部、1 位客戶沒有綜合卡，「險種」「狀態」兩欄整欄標不上；照標籤篩時它們算「還沒標過」，回答只多一句「可能漏」。

使用者時刻：
- 她問「停效的保單有哪些」→ 只有一份保單文件的那張也列得出來。
- 她說「張志明改成準客戶」→ 改一個地方，綜合卡上那行跟著變；之後 AI 重寫那張卡也不會改回去。
- 資料還少、沒有綜合卡的客戶，整理完一樣有標籤，「在意醫療的有誰」不漏。

## 決策（D-505，修訂 D-234、D-235、D-236；補 D-237、D-238）

1. **正本在實體清單**：`.system/entities.json` 每筆實體多 `tags`：`{欄: 詞 | [詞…]}`（單選一個詞、可多選清單；`""`／`[]` 是「看過、沒有」；沒有這個鍵是「還沒標過」）與 `tags_said`：她親口定的欄名清單。schema 2 → 3，大升級。
2. **綜合卡檔頭是渲染**：有綜合卡的照現在的寫法顯示那幾行（D-234 的格式不變），由程式照正本寫。
3. **誰寫正本**（都經程式，AI 不直接寫 `.system/`）：
   - AI 寫或更新綜合卡（照舊在檔頭寫標籤行）→ PostToolUse 驗過之後，程式把檔頭的標籤行抄進正本。`tags_said` 裡的欄不抄：照正本把那一行寫回卡上（她說的贏過 AI 重判）。
   - 沒有綜合卡的實體：製卡助手讀它掛的檔案卡判斷，跑 `kb entity tag <名稱> 欄=詞[,詞] …` 寫正本。
   - 她口述改（「改成準客戶」）：note 跑 `kb entity tag <名稱> 階段=準客戶 --said`，那一欄進 `tags_said`；有綜合卡就重寫那一行。
4. **補標籤**（D-236 擴大）：第八節加欄或詞時，那個型別**每個 active 實體**都記「補標籤」，不再只有有綜合卡的。有綜合卡的照現在，製卡助手只改標籤行；沒有的進同一批，製卡助手讀檔案卡、跑 `kb entity tag`。新實體整理完還沒有綜合卡的，也照這條補。
5. **照標籤篩、lookup、改字典都讀寫正本**：`entity list --tag` 不再讀卡；`profile tag rename|merge|remove` 改正本再重寫用到的綜合卡那一行；`impact` 照正本算。
6. **她手改綜合卡的標籤行**（Obsidian 裡改，沒經工具）：開對話時就認出（開場段一行），每週健檢再補一次；檔頭詞在字典裡的，照她改的抄進正本、算 `--said`（D-223：認出她改的、照她的意思做、做完在報告列出）；字典外或單選寫兩個的，記待處理問她。
7. **回答末尾那句**（D-238）：改成比對正本在這一回合的備份，連沒有綜合卡的也講。
8. **舊庫升級**：schema 2 → 3 時把每張綜合卡檔頭的標籤行抄進正本；沒有綜合卡、型別有標籤欄的 active 實體記「補標籤」。
9. **之後長出綜合卡**：第一次寫綜合卡時材料的 `header` 帶正本現有的標籤（三-2），AI 從那裡寫起；非她說的欄可以照新資料修正，寫完照第 3 點抄回正本；她說的欄不動。標籤不會因為有了綜合卡而清掉或重標。

## 資料與介面格式

`entities.json`（schema 3）一筆：

```json
{"id": "e-1a2b3c4d", "type": "保單", "name": "張志明十年定期壽險", "status": "active", "card": false,
 "tags": {"險種": ["壽險"], "狀態": "停效"}, "tags_said": []}
```

`kb entity tag 張志明 階段=準客戶 --said --json`：

```json
{"name": "張志明", "changed": ["階段"], "kept": [],
 "tags": {"在意": ["旅遊", "長照"], "階段": "準客戶", "家庭": ["已婚", "照顧長輩"]},
 "card": "客戶/張志明/張志明.md"}
```

`cards batch` 裡只補標籤的項目：

```json
{"entity_id": "e-1a2b3c4d", "name": "張志明十年定期壽險", "type": "保單", "tag_only": true,
 "cards": [{"id": "c-…", "path": "檔案索引/…md", "title": "…"}], "tags": {}, "tags_said": [], "reason": "補標籤（險種、狀態）"}
```

## 驗收準則

1. 新知識庫 `entities.json` 是 schema 3；schema 2 的 fixture `load` 後沒有 `tags` 鍵、`tag_filter` 全算 untagged。
2. 升級：schema 2 fixture（有卡有標籤 A、有卡沒標籤行 B、沒卡 C，型別都有標籤欄）`upgrade --finish` 後：A 的 `tags` 等於檔頭、B 沒有 `tags` 鍵、C 記了補標籤；字典外的詞進 `skipped`；`versions revert` 回得去。
3. `kb entity tag 張志明十年定期壽險 險種=壽險 狀態=停效`：沒有綜合卡也寫進正本；成功句一字不差；字典外、單選兩個、欄不屬這型別各一個拒絕測試。
4. 有綜合卡的實體 `entity tag … --said`：卡上那一行換、其他行與內文位元組不變、備份 by program；`tags_said` 有那欄。
5. hook：AI 寫綜合卡（合法）→ 正本跟檔頭一樣；`tags_said` 裡的欄 AI 寫了別的詞 → 正本不變、卡上那行被寫回正本的值。
6. `entity list --tag 狀態=停效`：沒有綜合卡、正本有 `停效` 的保單列出來；`counts` 數字對；沒帶 `--tag` 輸出跟改之前一樣（拿現有測試比）。
7. `profile add 標籤` 加欄：沒有綜合卡的實體也記補標籤；`cards batch` 項目有 `tag_only`、`cards`；有卡的照現在。
8. `profile tag merge 客戶 在意 健康 --into 醫療`：正本與卡都換、`impact.entities` 數對、有卡與沒卡的實體都算；revert 全回。
9. `lookup` 沒卡的實體也印標籤那行。
10. 回答末尾：這一回合 `entity tag` 給沒卡的實體加了詞 → `tell` 有 `<名稱>標了：…`；by program 的不算。
11. 手改：卡上標籤行改成字典裡的詞、卡較新 → 開場段有那一行（名稱最多 3 個）；`entity tag --from-card` 後正本照改、`tags_said` 加欄、句子一字不差、開場那行不再出現；字典外 → 不寫、回問句；健檢跑到時同樣處理，字典外記待處理 `tag_edit`；`test_budget` 開場字數照過。
12. 新實體整理完沒寫綜合卡 → 同一個整理派出只補標籤的項目。
14. 先只有一份資料、正本有標籤的實體，加第二份後寫綜合卡：`cards batch` 的 `header` 帶正本的標籤；寫完正本保留她說的欄、其他照卡。
13. 相關測試（entities、entity CLI、synthesis、output_log hook、profile tags、migrate、upgrade、lookup、plan、batches、cards CLI、lint 相關、rules synthesis、skill note、budget）過；全套照 process 只在發行時跑版號相關。
