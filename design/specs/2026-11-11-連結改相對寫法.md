# 連結改相對寫法（#66 甲）

日期：2026-11-11
狀態：設計中
版本：（發行後填）
來自：issue https://github.com/jielle2453/wiki-dev/issues/66 ；併入 B：無。#66 拆三支，這是甲；乙（外掛支援子夾與切換）、丙（上層的安裝、升級、清痕跡、守門）另寫。三支都在分支 `spec/外掛上層vault` 做，全部做完再測一輪。
區域：日程、整理成卡、延伸

## 目的

客戶把 Obsidian 開在知識庫的上層資料夾（知識庫是 vault 裡的一個子夾），或同一個 vault 接了兩個知識庫時，點日程頁、綜合卡「相關檔」、總目錄上的連結要開到**這個知識庫自己**的卡。現在的寫法 `[[<型別夾>/<名稱>/<名稱>|<名稱>]]` 是相對知識庫根的路徑，Obsidian 把它當 vault 根的路徑找，找不到才照結尾相符找：上層有同路徑的檔、另一個知識庫有同名實體時會開到別處，而且不報錯。

2026-11-11 實測（Obsidian 1.15.0，`app.metadataCache.getFirstLinkpathDest`；A、B 是同一個 vault 裡的兩個知識庫）：

| 寫法 | 從哪一頁 | 情況 | 結果 |
|---|---|---|---|
| `[[型別/乙/乙]]` | A 的 `系統/日程.md` | 上層夾也有 `型別/乙/乙.md` | 開到上層那份（錯） |
| `[[型別/丙/丙]]` | B 的 `系統/日程.md` | A 也有 `型別/丙/丙.md` | 開到 A 的（錯） |
| `[[型別/丁/丁]]` | A 的 `系統/日程.md`、A 的 `總目錄.md` | vault 根有 `型別/丁/丁.md` | 開到 vault 根那份（錯） |
| `[[../型別/乙/乙]]`、`[[../型別/丙/丙]]`、`[[../型別/丁/丁]]` | A、B 的 `系統/日程.md` | 同上三種 | 自己庫的（對） |
| `[[../../型別/乙/乙]]` | A 的 `型別/甲/甲.md` | 上層有同路徑 | A 的（對） |
| `[[./型別/丁/丁]]`、`[x](./型別/乙/乙.md)` | A 的 `總目錄.md` | 同上 | A 的（對） |

知識庫自己當 vault 根時，相對寫法也照樣對。

## 決策

D-541（修訂 D-280、D-315；jacky 2026-11-11 定，jielle2453 同意後才定稿）。

## 要做的事

1. **一個共用函式**算相對連結目標，放 `scripts/kb/_lib/paths.py`：`rel_link(page, target)`。兩個參數都是相對知識庫根的 posix 路徑（`page` 是連結寫在哪一頁，`target` 是要連到的檔）；回從 `page` 所在的夾算起的相對路徑，一律以 `./` 或 `../` 開頭，分隔用 `/`，不動副檔名。例子見「資料與介面格式」。
2. **日程頁**：`scripts/kb/_lib/agenda.py` 的 `linker(vault, ents=None, mark_removed=False)` 加參數 `page=MD_POSIX`，連結目標改成 `rel_link(page, where)` 去掉 `.md`。現有呼叫端不用帶 `page`（都是寫 `系統/` 底下那幾頁、深度一樣）；`scripts/kb/entity.py` 648 行的 panel 列是拿來在日程頁上找那一行的，要跟日程頁同一個寫法，也不帶。`money.py` 的呼叫端不動（#65 會整支拿掉）。
3. **綜合卡「相關檔」**：`scripts/kb/_lib/synthesis.py` 的 `_wiki(m)` 與 `file_section(mounts_of_it)` 多收那張綜合卡的相對路徑（`render_cache` 裡的 `rel`），連結寫成 `[[<rel_link(rel, m["path"]) 去掉 .md>|標題]]`。`file_section` 的其他呼叫端（測試、`_hers_file_section` 比對用的 `section`）跟著帶同一個 `rel`。
4. **總目錄**：`scripts/kb/_lib/cards.py` 的 `_summary_lines`、`_render_index` 三處 `({_link_target(…)})`，目標先過 `rel_link(INDEX_POSIX, …)` 再跳脫（結果是 `./…`）。
5. **讀連結的地方兩種寫法都要讀得懂**（舊頁還沒重寫、她手改過的都會留舊寫法）：`scripts/kb/_lib/renders.py` 的 `unlink`、`agenda.table_cell`，以及用連結文字比對的地方（`grep -n "unlink(\|_WIKILINK\|_LINK" scripts/kb -r`）。預期不用改（`unlink` 只取 `|` 後面或最後一段），補測試證明：同一行舊寫法與新寫法 `unlink` 之後相同，所以只是連結寫法不同不算她手改。
6. **舊庫升級時重寫一次**：`scripts/kb/_lib/upgrade.py` 的 `finish`，在 `k != "downgrade"` 那段 `_run_init(vault)` 之後，依序叫 `agenda.render(vault, turn_id)`、`cards.render_index(vault, turn_id)`、`synthesis.render_cache(vault, None, turn_id)`。三支本來就是「內容沒變不寫、寫前備進回合」，不加遷移表的列、不加版本記號；任何一支丟例外記 `ledger.log_error` 後繼續，不擋升級。綜合卡「相關檔」那段她手改過的，照 `render_cache` 現有的規則留她那份（D-223），不特別處理。
7. 改到的檔，同一個 commit 改 `ops/map-*.md` 那一列。

## 資料與介面格式

`rel_link(page, target)`：

| page | target | 回 |
|---|---|---|
| `系統/日程.md` | `01 顧客/李小姐/李小姐.md` | `../01 顧客/李小姐/李小姐.md` |
| `01 顧客/李小姐/李小姐.md` | `檔案索引/報價/2026/報價單.md` | `../../檔案索引/報價/2026/報價單.md` |
| `總目錄.md` | `01 顧客/李小姐/李小姐.md` | `./01 顧客/李小姐/李小姐.md` |
| `01 顧客/李小姐/李小姐.md` | `01 顧客/李小姐/附件.md` | `./附件.md` |

寫進頁面的樣子：

| 頁 | 舊 | 新 |
|---|---|---|
| `系統/日程.md` | `[[01 顧客/李小姐/李小姐\|李小姐]]` | `[[../01 顧客/李小姐/李小姐\|李小姐]]` |
| 綜合卡「相關檔」 | `- [[檔案索引/報價/2026/報價單\|報價單]]（2026-10-01）` | `- [[../../檔案索引/報價/2026/報價單\|報價單]]（2026-10-01）` |
| `總目錄.md` | `- [李小姐](01%20顧客/李小姐/李小姐.md)` | `- [李小姐](./01%20顧客/李小姐/李小姐.md)`（跳脫照現有 `_link_target`） |

`kb` 子命令的參數與 `--json` 輸出都不變（`kb home --json`、`kb lookup --json`、`kb entity panel --json` 裡的 `path`、`card_path` 仍是相對知識庫根的路徑，不是連結）。只有 `entity panel` 的 `line`、`match` 這類「頁面上那一行的字」會跟著日程頁變成新寫法。

## 驗收準則

1. `rel_link` 上表四列各一個測試，另加：`target` 與 `page` 在同一夾回 `./檔名`；路徑裡有空白、中文、`#` 原樣回、不跳脫。`python -m pytest -q tests/test_lib_paths.py` 綠。
2. 假知識庫有實體「李小姐」（型別夾 `01 顧客`、有綜合卡）與一條掛她的日程：`kb agenda` 重產後 `系統/日程.md` 那一行含 `[[../01 顧客/李小姐/李小姐|李小姐]]`，不含 `[[01 顧客/`。
3. 同一個假知識庫，李小姐掛一張檔案卡：`render_cache` 後綜合卡 `<!-- willy:檔 開始 -->` 到 `<!-- willy:檔 結束 -->` 之間每個連結都以 `[[../../檔案索引/` 開頭。
4. `總目錄.md` 的每個 `](` 後面都以 `./` 開頭（摘要那塊與檔案那塊都是）；`cards.index_broken(vault)` 仍回 False。
5. 舊寫法的日程頁（測試直接寫一份 `[[01 顧客/李小姐/李小姐|李小姐]]` 的頁並 `renders.record`）→ 跑 `agenda.render`：頁被重寫成新寫法，`系統/待處理.md` 沒有多出手改的項目，`renders.check` 回沒有手改。
6. 舊寫法的綜合卡「相關檔」（程式上次寫的、指紋有記）→ `render_cache`：那段被重寫成新寫法，`renders.keep` 沒被叫（不當成她手改）。她真的改過那段的（指紋對不上）照舊留她那份。
7. 她在日程頁把某一行的日期改掉、那一行的連結還是舊寫法：`apply_hand` 照樣認得出改了哪一條（跟連結是新寫法時結果一樣）。
8. `upgrade.finish` 從舊版升上來（測試照 `tests/test_lib_upgrade.py` 現有的做法造舊版知識庫，三頁都是舊寫法）：做完三頁都是新寫法；再跑一次 `finish`（同版本）三頁的 mtime 不變。三支裡任一支丟 `OSError`（測試換替身）時 `finish` 照常回結果、`.system/` 的錯誤紀錄多一筆。
9. 表格裡的連結照舊把 `|` 寫成 `\|`（`agenda.table_cell("[[../a/b|b]]")` 回 `[[../a/b\|b]]`）。
10. commit 之後「相關測試」全部加 `tests/test_repo_hygiene.py` 的 exit code 是 0。`tests/test_lib_money.py`、`tests/obsidian/money.test.js` 的結果另外列在回報（紅了不修）。

## 確認情境

確認放在三支都做完之後一起做，這裡先列甲的。在 `willy-測試` 裡造的假知識庫複本做，不碰真的知識庫。

1. （自動，Obsidian CLI）把假知識庫複製兩份成 `上層\willyA`、`上層\willyB`，`上層\` 放一份跟 A 某張綜合卡同路徑的假檔；兩個庫各有同名實體。在 Obsidian 開 `上層\`（已登記的測試 vault 底下也行），用 `Obsidian.com vault=<vault> eval code=…` 對 A、B 的 `系統/日程.md`、一張綜合卡、`總目錄.md` 讀 `app.metadataCache.resolvedLinks[<那一頁>]`：每一個目標都在同一個庫的夾底下，沒有一個落在 `上層\` 那份假檔或另一個庫。
2. （自動）同一份假知識庫直接當 vault 根開：`resolvedLinks` 每個目標都存在，`unresolvedLinks` 裡沒有程式寫的那幾種連結。
3. （人眼）在 Obsidian 點日程頁上的名字開到綜合卡；綜合卡的反向連結面板列得出日程頁。
4. （自動）`claude -p --plugin-dir <worktree>` 在舊寫法的假知識庫複本說「內湖李現在怎樣」：回答正常、沒有多出「你改了日程」這類待處理。
